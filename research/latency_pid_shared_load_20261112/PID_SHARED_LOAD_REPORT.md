# 共享GPU负载下的真实场景PI控制测试

## 结论与数据范围

当前默认PI可以降低平均渲染耗时，但不能在本轮自然共享负载下稳定对齐0.4 ms。仅27.73%请求进入0.38–0.42 ms，相对请求3000点的画质下降8.07825 dB。该实现暂不适合作为画质优先的实时生产默认。

在既有外部GPU任务继续运行时，用当前冻结office2 RGB-D模型、蒸馏Compensator、Tensor Core D、新准备及Mode40测试。分辨率2064×2208，完整2000帧重复三轮；每个视角交错执行固定3000点、最低预算256点和PI三种方法，共18000次单图调用。目标固定0.4 ms、允许区间0.38–0.42 ms，未根据结果改目标或选择样本。

|---|---:|---:|---:|---:|---:|---:|---:|
|请求3,000点|0.559869|0.695955|1.550099|2.15%|96.50%|2983.81|28.61496|
|固定256点（下限对照）|0.405327|0.538946|0.815427|22.03%|26.55%|256.00|18.70099|
|PI：目标0.4 ms|0.429970|0.557819|1.340799|27.73%|35.00%|466.23|20.53671|

PI有24.68%的请求达到256点下限；最长连续超过0.42 ms为78帧。固定256点仍有26.55%的请求超过0.42 ms。
PI相对固定3000点平均耗时差为-0.129899 ms，平均PSNR差为-8.07825 dB。这些差异同时受到预算与自然负载变化影响，不把交错测量视为完全相同外部负载的确定性因果对照。

## 负载与测量

- 正式计时窗口共69个监控样本，外部计算活动出现比例95.65%，GPU总利用率均值39.12%。
- 监控保留逐进程pmon与GPU频率、温度、显存和功耗；约1 Hz采样不能定位每个亚毫秒请求的精确竞争状态。
- 三方法在同一视角组内轮换顺序，视角组按90 Hz节奏提交；每种方法各一次单图请求，组内三个方法依次执行，不代表单方法端侧FPS。
- 全部单次CUDA Event耗时保留，不取每帧三次中位数、不因负载或耗时剔除样本。
- 请求3000点的对照保留原候选不足裁剪，实际平均2983.81点、最低2088点，没有补点。
- PID只用过去完成的Event反馈，不使用当前帧试渲染、GT、离线最优K或耗时曲线。
- 使用原生控制器的同一Event对完成计时；在原prepare已有发布同步后额外做非阻塞Query及日志读取，保证完整收集上一帧反馈。该遥测放在当前帧计时外，没有新增每帧等待、准备或渲染。
- prepare及网络不计入纯渲染目标；Host控制API耗时与额外遥测分别记录，不能将Host提交时间称作完整GPU完成时延。

## 控制开销与画质

- PI request/start/finish三个API的Host耗时中位数14.736微秒，p95 26.496微秒。这是共享环境下API区间实测，不是独占CPU/GPU下的额外端到端开销差值。
- 额外非阻塞Query和日志遥测中位数7.538微秒，计时外单独列出。
- 画质在计时结束后按记录的请求预算重放评价，逐项核对K/M/ratio；PSNR从不进入控制器。GT为原始RGB经INTER_LINEAR放大，非原生高分辨率真值。
- 图只展示第一轮原始逐帧耗时；PSNR采用σ=35帧展示平滑。CSV及表格采用原始单次结果。

## 可达性与限制

- 最低256点是当前配置的下限，不是数学上的全局最低成本。该对照若仍超时，说明不能靠本配置的继续减点消除所有超时。
- 同一K不保证同一耗时；GPU竞争、频率、视角覆盖面积、遮挡及ratio相关补偿都可影响工作量。
- 若大量请求停在下限、区间命中率仍低，应判定当前目标在该负载下不能稳定跟踪，不能把点数减少本身称作控制成功。
- 三轮分别从初始预算3000点启动；稳态和前90帧分别记录，未隐藏启动阶段。

## 后续方向

- 优先加入画质预算下限和目标不可达状态，避免为了追逐外部竞争导致的延迟尖峰持续损失重建质量。
- 对短时竞争噪声和可随K改变的持续工作量做区分，再验证滤波/抗饱和参数；本轮不根据评价结果改增益后替换原测试。
- 若引入当前视角成本预测，可改善持续工作量变化的响应，但不能承诺消除外部GPU抢占或达到硬时延上限。
