# 推理延迟控制V2：计时归因与控制状态修复

## 结论

此前“减到256点仍无法接近0.2 ms”的主要问题，在本次空闲GPU复测中来自计时边界。旧版CUDA Event分散在Python的start、render、finish调用两侧，把主机发射空档也反馈给PID；控制器通过减少K无法消除这部分时间，结果损失大量画质。

另一个独立、可复现的控制错误是：候选数受限后，旧位置式PI仍以初始3000点为基准，死区退出时可能在超时情况下继续加点。V2修复此问题，但完整轨迹上，修正计时后的旧PI与新PI差距很小。不能将主要收益归因于增量PI本身。

本轮只修改训练完成后的推理控制与独立计时接口，没有修改模型、训练、点选择算法或任何Rasterizer像素计算，没有覆盖服务器生产默认，没有commit/push。

## 1. 实验范围

- 数据：Replica office2 RGB-D，完整2000帧轨迹，原始1200×680 RGB，3次重复。
- GPU：RTX 3090；计时窗口内66个约1 Hz监控样本，未检测到外部GPU或明显外部CPU活动。
- 模型：同一冻结Master，43,197点；蒸馏Compensator、Tensor Core D、新准备路径、Mode40。
- 目标：0.2 ms，允许区间0.19–0.21 ms；初始请求3000点，范围256–8192，候选不足由原后端裁剪。
- 每帧只执行一次prepare及一次render。没有试渲染、未来帧预知、GT反馈或按测得耗时筛除样本。
- 五种方法轮换执行顺序，各6000条原始计时，合计30,000条。另行回放记录的请求预算评价PSNR，不保存渲染图片。
- 90 Hz约束的是包含五种方法的视角组调度，不能视作单方法显示FPS。

## 2. 发现的问题与实证

### 2.1 计时区间混入主机调度

旧路径为：C++ start记录begin → 返回Python → Python调用Renderer → 返回Python → C++ finish记录end。亚毫秒渲染可能在主机提交end前已完成，Event区间因此包含GPU空等主机的时间。

独立诊断对同一次渲染同时记录外层Event与原生Event，共224次请求。外层中位数0.137696 ms，原生中位数0.113008 ms，两者逐次差值的中位数0.024192 ms。这是独立诊断，不能把24 μs当作正式控制程序的固定扣除量；实际空档随Host工作量变化。

V2的原生Hook在同一个C++调用内，于输入更新和cudaGraphLaunch前后记录Event。它覆盖输入更新Kernel与完整渲染CUDA Graph，排除Python包装、输出Tensor分配、Graph冷构建。原生区间仍可能包含驱动发射间隙或真正的GPU竞争，不声称等于所有Kernel时间之和。

这属于测量边界修正，不是渲染Kernel加速。不能把旧外层0.2105 ms与新原生0.1722 ms直接解读为渲染器加速18%。

### 2.2 固定基准与死区的控制方向错误

CPU回归使用同一有效输入序列：先将有效候选限制为500点，再恢复候选池，经过一次恰好达到目标的反馈，随后输入0.212 ms超时反馈。

- 旧版预算从500增加至540，方向错误。
- V2预算从500降至485。

测试包含断言，并使用保留的V1 Core直接复现。没有通过手工改变旧代码制造差异。

### 2.3 积压反馈

旧实现一次poll可能对多条历史反馈连续更新当前控制状态。V2收回所有已完成Event，但同一轮只使用最新的有效样本决策。feedback_samples记录有效收据数，superseded_samples记录被更新样本取代的反馈，updates记录实际控制更新次数。

本轮正常全轨迹没有反馈积压或丢弃，因此这项修复的收益不来自本轮主表；独立GPU积压测试已覆盖。

## 3. V2实现

误差仍来自耗时EMA：e=(target−EMA(t))/target。连续死区误差为q=sign(e)max(0,|e|−0.05)。

在u=log(B)中计算：

```text
step = kp × (q − q_previous) + ki × q × dt − kd × (derivative − derivative_previous)
若q=0，或step与q方向相反：step=0
u_next = clamp(u_current + step,
               候选/请求上下限 ∩ 本次−25%/+8%的限速范围)
B_next = round(exp(u_next))
```

饱和和限速后的命令直接成为下一次的状态，不保留一个仍指向初始3000点的隐藏命令。dt仍使用提交时间且上限0.1秒。默认增益改为kp=3、ki=12、kd=0；误差EMA仍为0.25，原预算范围和每步限速保留。

该实现包含方向保护与连续死区，并非未经修改的线性PI。integral字段用于诊断裁剪后的累计状态，不应与V1的时间误差积分直接数值比较。

每个反馈仍绑定自己的frame、epoch、K、候选上限和提交时间。目标/视角切换会清空反馈历史并使旧epoch失效。Event环保持有界；没有新增逐帧等待，也没有缓存同帧视锥或改变网络ratio语义。

候选不足时仍为K=min(B,eligible)，网络ratio=min(1,B/M)，没有擅自改为裁剪后K/M。

只有原生计时的几行可直接比较渲染时间。旧外层方法在同轮、相同视角中保留，用于证明错误计时怎样改变预算和画质，不用于声明Kernel提速。

相同原生计时下，新PI较旧PI的PSNR仅提高0.0048 dB，命中率提高0.18个百分点，超过0.21 ms的总比例相同。新PI的主要价值是修正可复现的控制方向和积压状态错误，当前场景没有证据支持显著的额外画质或跟踪收益。

新版p99为0.207010 ms，最大0.221952 ms，仍有19/6000次超过0.21 ms；不保证硬实时。旧PI原生版本同样19次超过0.21 ms，最大0.257056 ms。不能以最大值单次差异声称稳定降低长尾。

### 4.1 为什么平均延迟低于0.2 ms

新版74.73%的请求已达到min(8192,当前有效候选数)，84.75%的请求耗时低于0.19 ms。上限和候选池约束使这些帧无法继续加点消耗剩余时间。因此14.93%的区间命中率不能称为精确锁定0.2 ms。

本轮没有提高8192上限、扩大候选池、故意增加工作或插入等待来制造命中率。作为0.21 ms软上限控制，新版约99.68%的请求合格；作为双侧严格跟踪，受控范围仍不足。

## 7. 尚未解决的边界

1. 当前结论来自office2 RGB-D、RTX3090空闲负载。V2尚未在真实外部重负载下重复完整轨迹，不能外推为共享GPU硬时延保证。
2. 减少K仍无法消除真正的GPU竞争、输出分辨率固定成本和主机发射成本。最低预算仍超时时应报告目标不可达，不能继续牺牲画质来假装控制成功。
3. 目前大部分请求受8192或候选池上限限制。下一次跟踪实验应先证明目标位于该视角允许预算的可控时间范围，再比较控制律；本轮没有改变这些约束。
4. 若目标是整个端侧帧延迟，应把准备、网络、Host调度和显示一起建模。当前0.2 ms只控制原生渲染区间，完整prepare的Host均值已大于0.2 ms。
